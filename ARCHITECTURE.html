askdocs · architecture

How askdocs Works

It answers questions about your documentation, on your machine, with no internet. This page explains every moving part in plain English — what each one does, and why it is built that way.

678chunks 70tests 1dependency 0databases
The idea

It looks things up. It does not learn.

The single most useful thing to understand: the model was never trained on your documents and never will be. Nothing about it changes, ever.

When you ask a question, askdocs finds the handful of paragraphs most likely to hold the answer, pastes them into the prompt, and asks the model to answer using only those. That is the whole trick. If you pasted the right paragraph into a chat window by hand and asked your question underneath it, you would have done the same thing.

Everything on this page is machinery for doing that automatically, across 678 chunks, reliably, without the model making things up.

Three words used throughout
chunk
A slice of a page — a few paragraphs. Search works on slices, because you want to hand the model one relevant passage, not a 70,000-character document.
embedding
A list of numbers describing what a piece of text means. Similar meanings get similar numbers, so "how do I make it fast" can find a page about performance without sharing a single word with it.
grounded
An answer is grounded when everything it says came from the retrieved sources. Ungrounded means the model invented something. Preventing that is most of the work.
The shape of it

Two phases that run at very different times

Almost every confusion about systems like this comes from mixing these up. One runs rarely and is slow. The other runs constantly and is fast.

Building is the slow part — it has to read every document and turn every chunk into numbers. Asking is fast because all that work is already done and sitting in a file.

The important part

How it avoids making things up

A small model running on your laptop does not go quiet when it is unsure. It writes something fluent, plausible and wrong, with exactly the same confidence as a correct answer. Telling it not to is not enough.

The prompt does say “use only these sources, and if they do not answer the question, say so”. A 3B model obeys that most of the time. Most of the time is not something you can put in front of people, so there are three checks that are plain code:

01

Refuse before even asking

If nothing found scores above a floor, askdocs answers “the documentation does not cover this” without calling the model at all.

Handing five irrelevant paragraphs to a small model is asking it to invent something, and it will oblige. This also saves you the 40 seconds of waiting.

02

Check every link it cites

After the answer is written, every URL in it is compared against what was actually retrieved. A cited link that was never in the prompt was invented — there is nowhere else it could have come from.

This is the most damaging failure of all, because a citation is exactly what makes an answer look trustworthy.

03

Refuse to accept unsupported claims

A long answer that cites nothing is not an answer. Either it came from the sources, in which case it can name them, or it did not.

When a check fails you see a blunt warning, the reason is written to the query log, and the command exits with an error code so scripts can catch it. Nothing is quietly swallowed. 

$ askdocs ask "what is the SLA uptime guarantee?"

The documentation provided does not answer this.

[best score 0.0091 < floor 0.0155]
[retrieved 12ms, no model call]
And it is tested, not assumed

eval/questions.yaml contains four questions the corpus deliberately cannot answer — things like the capital of Australia, and a plausible-sounding Kubernetes question. askdocs eval --refusal checks the model declines all four. That is the only way to know the guards actually hold.

Search

Why it searches two ways at once

There are two ways to find text, and each is bad at what the other is good at:

MethodGood atBad at
By meaning
vectors		 "how do I make it fast" finding a page about performance, with no shared words Rare exact strings. AEM_BACKEND_FETCH_FAILED means nothing to it
By keyword
BM25		 Exact identifiers, error codes, file names, config keys Anything worded differently from the document

A developer searching documentation does both constantly, so askdocs runs both and merges the results. The merge is done by position, not by score — a "0.82 similar" and a "14.3 keyword score" are not comparable numbers, and trying to weigh them directly means inventing a conversion factor and re-tuning it forever. Ranking sidesteps that: first place is first place either way.

A concrete example

The keyword index stores AEM_BACKEND_FETCH_FAILED both whole and split into backend, fetch, failed. So pasting the exact error finds it, and so does describing it in words.

Storage

Why there is no database

This is the decision people question most, so here are the measurements rather than an opinion.

Corpus sizeMemoryTime to search all of it, exactly
678 chunks — you are here2 MB1.2 ms
10,00029 MB1.4 ms
100,000293 MB15.6 ms
1,000,0002.9 GBwill not fit in 16 GB RAM

Vector databases exist to make search approximate, because checking millions of vectors one by one is too slow. You do not have millions. At your size askdocs checks every chunk and gets the exactly correct answer in about a millisecond.

Adding one would mean a large dependency to install offline, a server to keep running, another thing to back up, and slightly worse answers — in exchange for nothing. The storage code sits behind one setting, so if the corpus ever grows past about 100,000 chunks, swapping it is a one-file job.

Three plain files, written atomically so an interrupted rebuild never corrupts a working index:

index/
  chunks.jsonl     the text, plus url, title, breadcrumb, anchor
  vectors.npy      the numbers
  manifest.json    which model built it, and a fingerprint per document
Adding things

The two ways to extend it

Both are registries: write one file, import it, done. Neither requires touching the pipeline.

Connectors — new kinds of document

Two exist: .jsonl and .md. A connector answers two questions — "is this file mine?" and "what documents are in it?" — and everything downstream is unchanged, because it only ever sees a Document. 

@register
class ConfluenceConnector:
    name = "confluence"
    def claims(self, path):        # is this file mine?
        return path.suffix == ".confluence"
    def load(self, path, source):  # yield Documents

Skills — questions retrieval cannot answer

Ask "how many pages are indexed?" and searching the documents is useless: the documents do not know they were indexed. Without a skill, retrieval returns five arbitrary chunks and a small model invents a number from them — the exact failure this project exists to prevent.

Skills run before retrieval. The first one to claim a question answers it and generation is skipped entirely, so the answer is instant. A skill that crashes is skipped rather than taking the question down. 

$ askdocs ask "how many pages are indexed?"

The index holds 678 chunks from 183 documents (source: local).

Settings

Where settings come from

Four places, and the one furthest left always wins: 

command line flag   →   environment variable   →   askdocs.toml   →   built-in default

So you can keep sensible values in the file, override them per machine with environment variables, and override those for a single command: 

ASKDOCS_GENERATE_MODEL=qwen2.5:7b askdocs ask "..."
ASKDOCS_OLLAMA_HOST=http://gpu-box:11434 askdocs index
askdocs ask "..." --model llama3.1:8b --top-k 8

Run askdocs env and it lists every variable, its current value, and where that value came from. A setting that silently fails to apply is worse than one that is obviously broken.

One setting behaves differently on purpose

Changing the embedding model invalidates the whole index. Numbers from two different models are not comparable, so search would still return five chunks — simply the wrong five, with no error anywhere. askdocs refuses to run and tells you to rebuild instead.

Knowing it works

How quality is measured

One number matters most: how often the correct page appears in the five chunks retrieved. Almost every bad answer is a retrieval failure wearing a generation costume — if the right paragraph never reaches the prompt, no amount of prompt tuning saves the answer.

eval/questions.yaml holds 30 real questions with the URL that answers each. Two rules keep it honest: the questions are paraphrases, never copies of headings (copying makes the score trivially perfect and meaningless), and four of them are deliberately unanswerable. 

$ askdocs eval

Retrieval over 26 questions, top-5:
  recall@5  85%
  MRR       0.71

PASS: recall 85% meets the 80% threshold.

It exits non-zero below the threshold, so it can gate a commit or a build the same way a test suite does.

Everything that does not need a model is verified against your real data. Everything that talks to a model is written against Ollama's documented API and has not executed once. Install Ollama, run askdocs index, and the first real run will find whatever is wrong there.

One thing worth checking first

Your machine reports a second display device in an error state. If that is a real graphics card with a missing driver, answers would go from about 40 seconds to a few seconds, and a larger, more accurate model would become practical. It is the biggest possible improvement for no code at all.
