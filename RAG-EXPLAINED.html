How this RAG works

The model has never read your AEM documentation and never will. Everything in this codebase exists to find the right paragraphs, hand them over, and catch the answer if it drifts.

The idea

Don't ask it to remember. Hand it the page.

RAG stands for Retrieval Augmented Generation. Strip the jargon and it is one move: instead of hoping a language model memorised your documentation, you find the handful of paragraphs that actually answer the question, paste them into the prompt, and say answer using only these.

That move creates two new problems, and this repository is mostly about those two. First, finding the right paragraphs is hard — the words someone types rarely match the words on the page. Second, a small local model handed irrelevant context does not go quiet. It produces something fluent, plausible and wrong, with exactly the confidence of a correct answer.

So the work splits across two clocks. Build time runs occasionally and turns 183 pages into something searchable. Ask time runs on every question and has to be fast, and careful.

Clock one · askdocs index

Build time: 183 pages become 678 searchable pieces

Slow, occasional, entirely offline. Five steps, each one a file, each one handing its output to the next.

corpus → index

01
sources/jsonl.py · sources/markdown.py · sources/__init__.py

Read the files.

Each line of aem-live.jsonl becomes a Document — id, url, title, text. A registry picks the right reader by file extension, which is why nothing further down the pipeline knows or cares where the documents came from. Adding a new source never touches the pipeline.

02
normalize.py

Scrub the junk.

The least glamorous file, doing the most work. AEM pages exported to Markdown draw every block as an ASCII box table — +---+---+ rules and pipes. On this corpus that box art is 40.7% of every character. Useless boxes get deleted; useful ones (error-code tables, card lists) get rewritten as plain sentences. Anchor ids are harvested on the way out, which is what lets a citation link to the exact section rather than the top of the page.

03
chunk.py

Cut each page into pieces.

Slices at every ## heading, then packs small neighbours together up to roughly 700 tokens. Every piece gets a breadcrumb — Page > Section — glued to its front. That breadcrumb matters more than it looks: two chunks both headed “Limits” from different pages are nearly identical to a machine, and the breadcrumb is the only thing telling them apart.

04
ollama.py

Turn each piece into numbers.

Every chunk goes to the local Ollama server and comes back as 768 numbers describing its meaning. Written against the Python standard library with no requests dependency, because this has to install and run on a machine with no internet.

05
store.py

Write it to disk.

Three files land in index/: the chunk text, the number vectors, and a receipt recording which model built it and when. A keyword index is built in memory alongside. There is deliberately no vector database — 678 × 768 numbers is 2.1 MB, small enough that a plain matrix multiply returns exact nearest neighbours in about a millisecond. The write is atomic, so a crash mid-build never leaves a half-made index behind.

pipeline.py conducts those five steps. It also hashes every page, so a re-index only re-embeds the pages that actually changed.

Clock two · askdocs ask

Ask time: seven steps, three of them refusals

Runs on every question. Note how much of it is not retrieval or generation at all, but checking.

question → answer

01
skills/

Can a skill just answer this outright?

An escape hatch for questions the documents cannot answer about themselves. “How many pages are indexed?” is not in any document — the documents do not know they were indexed. Retrieval would return five arbitrary chunks and a small model would invent a number from them. So a skill catches the question by pattern and answers from the manifest. Instant, and no opportunity to make anything up.

02
ollama.py

Turn the question into numbers too.

Same embedding model that built the index — and the CLI refuses to continue if the setting has changed since. Vectors from two different models are not comparable, and the failure is silent: you would still get five chunks back, simply the wrong five, with no error anywhere.

03
retrieve.py

Find the five best chunks, two different ways.

The heart of the system, and the section below is about nothing else.

04
grounding.py — guard one

Nothing good came back? Stop here.

If the best chunk scores below a floor, refuse without calling the model at all. Handing five irrelevant passages to a small model is an invitation to invent, and it obliges.

05
answer.py

Build the prompt and stream the reply.

The prompt is the whole mechanism: use only these sources, say the documentation provided does not answer this if they fall short, cite the URL of everything you used. The chunks arrive carrying their url, title and breadcrumb — without those the model has five anonymous walls of text and can cite nothing.

06
grounding.py — guards two and three

Check the citations are real.

Every URL in the answer must be one that was actually in the prompt, and a substantive answer must cite something.

07
logs.py

Write down what happened.

One JSON line per query: the question, which chunk ids came back, the timings, whether grounding passed. The chunk ids are the valuable part — almost every bad answer is a retrieval problem wearing a generation costume.

The centrepiece · retrieve.py

Two searches, because neither one is good enough alone

Every question runs through both, and the results are merged. They fail in opposite directions, which is exactly why they are paired.

Vector search

Understands meaning, forgets exact strings

  • Matches “how do I make it fast” to a page about performance, with no shared words.
  • Handles paraphrase, synonyms, roundabout phrasing.
  • Weak on rare literal strings — the numbers for AEM_BACKEND_FETCH_FAILED look much like the numbers for any other error code.

Keyword search · BM25

Nails exact strings, misses rewording

  • Finds helix-query.yaml and AEM_BACKEND_FETCH_FAILED instantly.
  • Indexes identifiers whole and split, so “backend fetch failed” finds the error code too.
  • Blind to anything worded differently from the page.

Merging them · Reciprocal Rank Fusion

The two are combined by rank position, not by score. That is a deliberate choice: a similarity of 0.82 and a BM25 score of 14.3 are not the same kind of number, and adding them means inventing a scale factor and re-tuning it every time either side changes. Ranking sidesteps the problem entirely — first place is first place on both lists.

The guards · grounding.py

Three checks that don't depend on the model behaving

Prompt instructions alone do not stop invention. A small model follows them most of the time, and “most of the time” is not a guarantee you can put in front of users. So each check is mechanical, and none needs a second model call.

Before

Refuse when nothing relevant was found

If the top chunk scores below the floor, the question never reaches the model. Cheapest guard in the system, and the one that prevents the most damage.

After

Every cited URL must have been retrieved

A URL that was never in the prompt is fabricated by definition. This is the most damaging failure to let through, because a citation is precisely what makes a wrong answer look trustworthy.

After

A real answer must cite something

Either it came from the sources, in which case name them, or it did not. An ungrounded answer also exits non-zero, so the whole thing stays scriptable.

The outlier

One page — Frequently Asked Questions — produced 146 chunks on its own, over a fifth of the entire index from a single line of the file. That is intentional. When a heading carries its own anchor link, the chunker keeps that section standalone instead of packing it with its neighbours. On an FAQ page every question is an anchored heading, so each question and its answer becomes one chunk. It has to work that way: glue three unrelated questions together and the answer can only link to one of them, so the citation points at the wrong question.

182 ordinary pages ≈ 532 chunks  +  the FAQ's 146  =  678

The number that matters · evaluate.py

Recall@k, not vibes

eval/questions.yaml holds questions paired with the page that should answer them. The harness asks each one and measures recall@k: the share of questions where the correct page actually appears among the retrieved chunks.

That metric is chosen deliberately. If the right passage never reaches the prompt, no amount of prompt tuning saves the answer — so retrieval is where the measurement belongs. It also only needs the embedding model, not the chat model, which means it runs in seconds and returns the same result every time.

askdocs eval --refusal tests the opposite failure: questions the corpus genuinely cannot answer, checking that the system refuses rather than improvises. That one does need the chat model, and is correspondingly slower.

In one paragraph

The generation step is the small part

A small local model will produce a confident, fluent, wrong answer whenever you give it bad context. So this codebase spends almost all of its effort at the two ends: normalize.py, chunk.py and retrieve.py making sure good context arrives, and grounding.py with evaluate.py making sure a bad answer gets caught instead of shipped. The part in the middle, where the model writes the prose, is the piece that needed the least work.
